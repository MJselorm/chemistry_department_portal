# Architectural Decisions and Active Constraints

This file records decisions evidenced by the implementation or checked-in operational documentation. It does not invent the historical discussion that led to them. Where alternatives or rationale are not recorded, that uncertainty is explicit.

| Decision / active state | Evidence and reason | Alternatives considered | Consequences | Status |
|---|---|---|---|---|
| Firebase Authentication is the identity provider; FastAPI verifies Firebase ID tokens. | `frontend2/AuthContext.jsx`, `backend/app/firebase.py`, and `backend/app/security.py` implement client sign-in and server verification, including revocation checks. | Historical alternatives are not recorded. | Protected API calls use bearer tokens; the backend must have valid Firebase Admin credentials. | Active |
| Database roles, not client profile data, authorize privileged operations. | `get_current_user`, `require_admin`, `require_super_admin_mfa`, and admin routers read/verify the database role and MFA claims. | Historical alternatives are not recorded. | UI route guards are only UX; sensitive changes require backend dependencies and transactions. | Active |
| SQLAlchemy models plus Alembic are the schema authority. | `backend/app/database.py`, domain model modules, `backend/alembic/env.py`, and numbered revisions; root docs state not to use `create_all()` for app schema. | Historical alternatives are not recorded. | Model/schema changes require reviewed migrations and deployment coordination. | Active |
| PostgreSQL is the production database; local configuration can use SQLite. | `backend/app/config.py` validates production database backend; `database.py` constructs the engine. | Historical alternatives are not recorded. | PostgreSQL-specific migrations/indexes and transaction behavior must be validated against PostgreSQL, not only SQLite. | Active |
| Browser code accesses application data through FastAPI, not Supabase credentials. | Frontend uses `client.js`; Storage operations use backend `storage.py` with server-side configuration. | Direct browser access is not documented as an alternative. | Service-role credentials remain server-only; private academic files are streamed/signed through the API. | Active |
| Directory media and academic resources use separate Storage policies. | Configuration and storage code use a directory-media bucket and private academic-resources bucket; README documents public directory-media URLs and private academic resource access. | Historical alternatives are not recorded. | Do not upload confidential imagery to the public media bucket; do not expose academic bucket credentials. | Active |
| The frontend is a Vite-built React SPA; the API is a separate FastAPI service. | `frontend2/` app structure, `frontend2/vercel.json`, and `render.yaml`. | Historical alternatives are not recorded. | SPA routes need fallback rewriting; API CORS must match deployed frontend origins. | Active |
| The frontend uses one shared API client and endpoint registry. | `frontend2/client.js` and `frontend2/endpoints.js` centralize bearer handling and route strings. | Historical alternatives are not recorded. | New feature calls should reuse these helpers rather than introduce another client. | Active |
| Some backend-only tables enable RLS and revoke browser-role grants. | Alembic migrations enable RLS and revoke `anon`/`authenticated` access for selected privacy, role, notification, and mentorship tables. | Historical alternatives are not recorded. | RLS is not uniform across every table; keep the trusted backend database identity and inspect each migration. | Active, table-specific |
| Mentorship matching uses explicit configurable weights and stores an explainable breakdown. | `backend/app/services/mentorship.py` centralizes `MATCH_SCORE_WEIGHTS`; the scorer accepts a weight map and migrations persist score factors. | Historical tuning alternatives are not recorded. | Ranking changes should update focused tests and documentation; optional factors are not all treated as mismatches. | Active |
| Privacy APIs currently expose two route families. | `backend/app/routers/privacy.py` mounts `/privacy`/`/admin/privacy` and `/api/privacy`; schemas/status sets differ. | Whether one family is intended to be deprecated is not recorded. | Keep both documented; do not add another family or assume identical request/response semantics. | Active compatibility state; consolidation is undecided |
| Operational history is not fully represented by repository documentation. | Existing `EVENTS.md` and `PRIVACY_REQUESTS.md` contain statements that differ from current routers/roles. Deployment state is not available from source alone. | N/A | Verify source and target environment before changing policy; update focused docs when behavior changes. | Active constraint |
